# 群内机器人同行互聊停止机制设计规格

- 状态：待用户审查
- 日期：2026-11-04
- 基线：`5bb54f1`（分支 `feat/bot-loop-stop`，本规格只落文档，不改代码）
- 需求来源：用户口头报告「当群里有两只以上的大肥鱼时，他们会一直聊下去且不会停止直到人工关闭服务」+ 四轮澄清（期望行为 = 在不适合聊的时候停、四个停止条件全选、部署拓扑 = 两个独立服务实例、识别机制 = 方案 A wxid 互认名单）
- 预期文档位置与本文件一致：`docs/superpowers/specs/2026-11-04-bot-loop-stop-design.md`

---

## 1. 背景与问题（根因）

两个独立部署的 DeepFeiyu 实例各登录一个微信号，同在一个微信群、都开启自动回复时，会形成 A→B→A 无限互聊，只能人工关闭服务终止。

根因（已核实的代码事实）：

1. 每个实例只过滤**自己账号**发出的消息：`rules.check` 对 `msg.is_self` 直接拒绝（`app/rules.py:90`）。
2. 群里**另一个机器人号**发来的消息，对本实例就是普通入站消息（`is_self=False`），与真人消息无差别地走完整策略（`app/wechat/manager.py:631`）。
3. 触发条件任一成立即成环：`group_need_at` 关闭；或对方回复文本里带 `@大肥鱼` 被 `mentioned()`（`app/rules.py:33`）认成点名（两个号人设同名时高度可复现）；或两边都开了主动搭话。
4. 现有"刹车"全是**账号级限速**：`min_interval_sec=3`、发送层冷却 12–25s、`daily_limit=300`（`app/config.py:181`）。它们只降频，**没有任何一层能识别"对方也是机器人"**；日上限设为 0 时完全无界，只能人工关服务。

## 2. 已确认决策

| 项 | 结论 |
|---|---|
| 期望行为 | 聊本身可接受，**在不适合聊的时候停**（不是彻底禁止互聊） |
| 停止条件（四条全选） | ①互聊轮数超限就收尾；②长时间没真人参与就停；③真人一开口就让位；④按时段与人工接管停 |
| 部署拓扑 | **两个独立服务实例**，无共享状态；各实例独立、对称判定 |
| 识别机制 | **方案 A：wxid 互认名单**（否决 B 前缀标记、C 双信号，见第 4 节） |
| 恢复方式 | 真人消息自动重置；不加控制台按钮（v1） |
| 默认姿态 | `bot_peers` 留空 = 完全保持现状，机制不生效 |

## 3. 技术事实（已核实）

1. **入站消息带发送者标识**：weixin4 群消息 `sender_id` 统一存 wxid（`app/wechat/weixin4_driver.py:1127`）；wcferry 群消息可能只解析出昵称、拿不到 wxid（`app/wechat/base.py:587` `unique_sender_id` 注释）。
2. **wxid 在控制台可见可抄**：群聊发送者展示为 `昵称(wxid)`（`app/wechat/base.py:600` `sender_label`）。
3. **策略判定入口唯一**：所有非自己消息都过 `rules.check(cfg, account, chat, msg)`（`app/wechat/manager.py:633`），返回 `(allowed, reason)` 并发布 `policy` 事件供控制台"为什么不回"展示。
4. **自己的消息分流**：服务发出的消息回声在 `handle_message` 早期被 `_outbound_echo` 吞掉（`app/wechat/manager.py:587`）；能走到 `if msg.is_self:` 分支（`:623`）的只有**人工在手机/桌面端直接发的消息**；AI 回复入库 `source='agent'`（`app/db.py:1061` 统计口径）。
5. **配置合并**：`config.save()` 对 patch 深合并（`app/config.py:637`），`auto` 段新增键不需要迁移；`PUT /api/settings` 原样透传（`app/main.py:1093`），前端 settings 表单在 `app/static/app.js:2296` 汇总 `auto` 字段。
6. **键值存储现成**：`db.kv_set/kv_get`（`app/db.py:1310`），朋友圈等模块已在用，可存每会话状态，无 schema 迁移。
7. **聚拢窗口**：`_schedule_reply`（`app/wechat/manager.py:704`）把短时间内的多条入站合并成一轮回复——真人消息与同行消息撞在同一窗口时天然合并为一条回复。
8. **`DEFAULTS["auto"]` 现有键**（`app/config.py:181`）：`group_need_at=True`、`min_interval_sec=3`、`daily_limit=300` 等，本设计只增不改。

## 4. 方案取舍

| 方案 | 结论 |
|---|---|
| **A：wxid 互认名单** | **采用**：判定确定性、不依赖消息内容；控制台可抄 wxid；两实例各自配置互不依赖，天然支持独立部署 |
| B：`auto.prefix` 内容标记识别 | 否决：默认前缀为空、两边都要先配置；前缀对群友可见改变现有观感；真人手打同前缀会误判；其合规价值（AI 内容标识）与本需求正交，出站 `auto.prefix` 能力保持不动即可 |
| C：A + B 双信号 | 否决：只在"wcferry 拿不到 wxid"的窄场景多出收益，配置与测试面翻倍，YAGNI |
| D：直接全局禁止回复同行 | 否决：与已确认决策冲突——用户要的是"在不适合聊的时候停"，允许有限互聊 |

## 5. 设计

### 5.1 识别

- 新配置 `auto.bot_peers: list[str]`（对方机器人 wxid 名单，全局）。非法类型按空名单处理（对齐 `rules._policy_list` 容错风格）。
- 判定 `is_peer(msg)`：入站消息 `msg.sender_id` strip 后 ∈ 名单。**sender_id 为空 → 按真人（fail-open）**，方向是维持现状，不误伤真人。
- 已知限制（写入文档与 Issue）：
  - wcferry 群通道解析不出 wxid 时机制退化为不生效；
  - 群里**未登记**的其他机器人按真人处理——"两只以上"要求每只都登记到对方实例的名单里。

### 5.2 状态机（每个**群聊**会话一份，kv 键 `botloop:{chat_uid}`）

状态仅两字段：`rounds`（本会话已**放行**的同行消息数）、`last_human_ts`（最后一条真人消息时间）。

生效范围：`bot_peers` 为空时观察函数整体短路、零开销（未启用用户完全不受影响）；名单非空时也只为**群聊**会话建立/更新状态——私聊与本机制无关（闸门只在 `msg.is_group` 时评估），不写状态。

| 事件 | 动作 |
|---|---|
| 会话首见消息 | 初始化 `rounds=0`、`last_human_ts=now`（纯机器人群从此时起计闲置） |
| **真人消息**（入站、非 system、发送者非同行；或本人手动发的消息 = `is_self` 且非服务回声分支） | `rounds=0`、`last_human_ts=now`——即**让位 + 重新激活**：优先回应真人，互聊从头计数；聚拢窗口内与同行消息合并回复（现有行为），真人的话必然被回应 |
| 同行消息，闸门评估（放行前） | ① `bot_chat_max_rounds>0 且 rounds>=N` → 拒绝，原因「机器人互聊已达轮数上限」；② `bot_chat_idle_stop_min>0 且 now-last_human_ts>=X*60` → 拒绝，原因「机器人互聊长时间无真人参与」；否则放行 |
| 同行消息的回复**真正开始生成时**（`_auto_reply_run` 拿到会话锁后） | `rounds+=1`；若 `rounds==N` → 标记**本轮收尾**。计数放在这里而非放行时：`_fire_reply` 窗口到期会重跑 `rules.check`，提前计到 N 会把第 N 条自己拦下；拿到锁后计数保证每轮回复只计一次 |
| AI 自己的回复（`source='agent'` 回声、服务出站） | 不是真人事件，不参与状态机 |

**停止后的恢复**只有两条路：群里出现真人消息（自动重置两字段），或用户本人在群里发一条消息（本人=真人）。不设控制台重置按钮（v1 非目标）。

### 5.3 接入点与判定顺序

- `rules.check`：同行闸门插在「人工接管中」检查（`app/rules.py:121`）**之后**、白/黑名单（`:124`）**之前**，且仅当 `msg.is_group` 且 `is_peer(msg)` 时评估。`rules.check` 保持只读纯判定。
- **现有闸门对同行消息照常全部生效**：工作时段、人工接管、日上限、`min_interval_sec`、黑白名单、`group_need_at`——停止条件④由此覆盖，并用测试固化。
- `manager.handle_message` 挂钩（状态写入集中在新模块，且仅在 `bot_peers` 非空且消息属于群聊时执行）：
  - 非 self 消息：判定前先分流——非同行且非 system → `reset`；同行 → 交 `rules.check` 闸门；
  - `if msg.is_self:` 的非 soft_echo 分支（人工手机发言）→ `reset`；
- 计数与收尾在 `_auto_reply_run`：拿到会话锁、进入生成前对 burst 调 `count_burst`（含同行消息才计），返回 `True` 即收尾轮，经 `_build_prompt(wrap_up=…)` 注入收尾指令（见第 5.2 节表格的时机说明）。
- 新模块 `app/botloop.py`（与 `rules.py` 平级，不新建顶层目录）：`is_peer` / `observe` / `count` / `reset` / 闸门读数 / 收尾标记查询，kv 读写与配置读取都收在这里。

### 5.4 收尾行为

第 N 条被放行的同行回复，在提示词尾部追加收尾指令（如"这是本轮对话的最后一条，请自然收尾道别"），由模型生成自然结束语，不写死话术。**对称副作用**：两个实例会在同一条消息上各自触发收尾，群里可能同时看到两句道别——不影响停止正确性，先接受，观感不佳再优化（后续可选）。

## 6. 参数与控制台

`auto` 段新增 3 键（`config.save` 深合并，接口层不改）：

| 键 | 默认 | 含义 |
|---|---|---|
| `bot_peers` | `[]` | 同行 wxid 名单；**留空 = 保持现状（机制关闭）** |
| `bot_chat_max_rounds` | `8` | 本账号最多回同行 8 条（两边对称，合计约 16 条后双双收尾）；`0`=不限 |
| `bot_chat_idle_stop_min` | `15` | 纯机器人聊满 15 分钟无真人发言即停；`0`=不限 |

控制台「自动回复策略」页（`app/static/index.html` + `app/static/app.js` settings 表单）新增 3 个字段；名单输入框提示"只填机器人号的 wxid，留空不启用互聊停止"。

## 8. 测试计划（全部用合成 wxid，如 `wxid_peer_test`）

1. **识别**：命中/未命中/空 sender/`bot_peers` 非法类型（null、单字符串、混入 null）→ 容错不崩、按空名单。
2. **轮数**：放行到第 N 条；第 N 条带收尾标记；N+1 拒绝且 reason 可读；真人消息重置后重新计数；`N=0` 不限。
3. **闲置**：满 X 分钟拒绝；真人刷新计时后恢复；首见初始化为 now；`X=0` 不限。
4. **让位**：真人入站（含 emoji/pat）与本人手动 `is_self` 消息都重置；`source=agent` 回声不重置；system 消息不重置。
5. **既有闸门对同行消息照常**：工作时段外、人工接管中、日上限已满、`group_need_at` 未 @、黑名单命中——各一条拒绝用例。
6. **fail-open 与范围**：无 wxid 的同行消息按真人放行；私聊同行消息不进状态机（行为=现状）。
7. **持久化**：状态写 kv 后重新读取仍在；旧版本忽略未知 kv 键（不测，靠 kv 自由格式天然成立，规格里说明）。

## 9. 风险、回滚与合规

- **误判方向**：空 wxid fail-open → 最坏维持现状（继续互聊）；唯一"少回"风险是把真人 wxid 误填进名单——输入框提示语防御。
- **可观察性**：拒绝照常发布 `policy` 事件，控制台"为什么不回"直接显示轮数/闲置原因。
- **已知边缘**：重启水位补推的旧 `is_self` 消息可能被当真人重置一次，影响仅是互聊多续几条，不破坏停止保证。
- **回滚**：revert 提交即可；配置键留着无害（空名单=关闭）；kv 状态旧版本自动忽略；**无数据库迁移**。
- **合规**（AGENTS.md 6.2 / 9）：wxid 只落本地 `data/config.json`（对齐 `send.forbidden_wxids` 既有做法）；测试/文档/Issue 全部用占位符与合成数据；不改许可与法律文档；不新增依赖、不改 `vendor/`；Issue 由人类提交，AI 不开 Issue、不推送。

## 10. 验收标准

1. 登记 `bot_peers` 后：≤N 条内正常互聊；第 N 条为收尾；之后不再回复同行，控制台策略给出可读原因；
2. 无真人发言满 X 分钟停止回复同行；真人消息（含本人手动发的）重置计数与计时并恢复互聊；
3. 时段/人工接管/日上限/`group_need_at`/黑名单对同行消息照常生效（有测试为证）；
4. 未配置名单、sender 无法识别、私聊场景：行为与现状完全一致；
5. 全量 `pytest -q` 通过，或如实列明环境性失败与原因；
6. `docs/使用说明.md`、`CHANGELOG.md` 同步；无真实 wxid/聊天记录/密钥入库。

## 11. 非目标与后续可选

- 非目标：私聊互聊防护、跨实例状态同步、方案 B/C 识别、自动发现 wxid、控制台状态重置按钮、主动搭话新闸门。
- 后续可选（本次不做）：控制台"重置互聊状态"按钮；收尾去重（避免两边同时道别）；按通道自动降级到昵称识别。

## 附录 A：Issue 草稿（供人类提交，AI 不代开）

> **标题**：[缺陷] 群里两个机器人号无限互聊，只能人工关闭服务

- **版本 / 提交**：由提交者填写（本设计基线 `5bb54f1`）
- **环境**：Windows / Python 3.12 / 微信版本与通道（wcferry、weixin4、webhook）由提交者填写
- **复现步骤**：
  1. 两个独立 DeepFeiyu 实例各登录一个微信号，均开启全局自动回复；
  2. 两个号加入同一个群；确保触发条件成立（`group_need_at` 关闭，或回复文本带 `@对方昵称`，或两边开了主动搭话）；
  3. 任一机器人先发一条消息，观察两个号开始互相接话。
- **期望结果**：互聊在轮数/真人缺席/真人插话/时段与接管任一条件命中时停止，无需关闭服务。
- **实际结果**：两号持续互聊直到人工关闭服务；日上限设 0 时完全无界。
- **日志 / 截图**：控制台 `policy` 事件（**须脱敏**：wxid 用占位符、聊天内容裁剪）。
- **出现频率与影响**：多号同群场景必现；影响 = 无限发送、打扰群友、消耗额度。
- **范围**：改识别与互聊状态机、配置与策略页字段、测试与文档；**不改**私聊策略、跨实例同步、出站 `auto.prefix`、`send.*` 限速、主动搭话闸门。
- **风险**：安全（wxid 仅本地配置）、隐私（不新增外联）、平台规则（降低无界发送）、许可（无）、兼容（无迁移）。
- **方案取舍**：采用 wxid 互认名单（确定性、双实例独立）；否决前缀标记（配置面/误判）、双信号（YAGNI）、全局禁互聊（与期望行为冲突）。
